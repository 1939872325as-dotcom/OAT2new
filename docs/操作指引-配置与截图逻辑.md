# OAT 操作指引 —— 配置与截图逻辑

> 依据:RMA-MUN/OnmyojiAuto `main`(v2.3.4)真实源码逐文件核对,以及你本机 v2.3.3 的运行日志。
> 文中每条结论都带 `文件:行号`,可自行复核。凡是推断而非直接读到的,我都标了「推断」。

## 一、配置文件总览:谁管什么、改完要不要重启

| 文件 | 管什么 | 何时读取 | 改完要重启吗 |
|---|---|---|---|
| `OAT/tools/settings.json` | 全局行为:识别模式/阈值、**抓屏模式**、窗口排列、MuMu 目录、主题 | **程序启动时读一次**(`settings.py:13-15` 模块级 `open`) | **要** |
| `OAT/source/mode.json` | 模式名 → 目录名 的映射 | 启动时读入 `MODE_MAPPING`(`source/__init__.py:16`) | **要** |
| `OAT/source/<模式>/config.json` | 该模式的图片模板、OCR 文字、点击方式、`next_image` 链路 | 每次开始挑战时读 | 不用(下一轮生效) |
| `OAT/source/<模式>/*.png` | 模板图 | 同上,按需加载 | 不用 |
| `OAT/config/config.yaml` | 只有背景图/图标名 | 启动时 | 要 |
| `OAT/config/update.json` | 忽略更新的版本列表 | 检查更新时 | 不用 |
| `OAT/source/huijuanshuafen/config.json` | 绘卷刷分专用区域参数(突破券区域等) | 每轮 | 不用 |

**最重要的一条**:`settings.json` 是**启动时一次性读入内存**的。运行中手改文件不生效;更坑的是
`update_settings()` 会把**内存里那一整份 dict** 写回磁盘(`settings.py:62-65`):

```python
settings_data[key] = value
with open(settings_file_path, 'w', ...) as f:
    json.dump(settings_data, f, ensure_ascii=False, indent=2)   # ← 整份覆盖
```

所以**程序开着的时候手改 `settings.json`,改动随时会被一次无关的保存操作整份覆盖掉**。
手改铁律:**先完全退出程序,再改文件,再启动**。

## 二、截图逻辑(完整链路)

### 2.1 两条路径的分岔点

识别引擎取帧只有一个入口:`OpenCVRecognitionEngine.capture_screenshot()`
(`OAT/pipeline/recognition_opencv.py:116-126`):

```python
def capture_screenshot(self) -> Optional[np.ndarray]:
    if self.hidden_window:              # 后台运行模式(日志里的“已启用后台运行模式”)
        if self.backend is not None:
            img = self.backend.screenshot()      # 路径 A：模拟器 IPC 通道
            ...
    ...
    return self.window_capture.capture_window()  # 路径 B：PrintWindow / BitBlt
```

| | 路径 A:模拟器 IPC | 路径 B:窗口截图 |
|---|---|---|
| 何时走 | `hidden_window=True` **且** `backend` 不为 None | 其余所有情况 |
| 实现 | `NemuIpc` / `MumuCapture`(`emulator/mumu_backend.py:12,15`) | `WindowCapture`(`tools/GetDC.py`) |
| 图像参考系 | **1280×720**(`emulator/backend.py:9`) | **客户区实际尺寸** |
| 受 `capture_window_mode` 影响吗 | **完全不受影响** | 就是它 |

`backend` 什么时候不是 None(`recognition_opencv.py:52-66`):

1. 显式:`settings.EMULATOR_TYPE == "mumu12"` 并提供 hwnd;
2. **自动**:`hwnd` 通过 MuMu 句柄树校验 → 挂 `MumuBackend`(`_create_mumu_backend_for_hwnd`,第 81-95 行)。
   校验方式是 `build_handle(int(hwnd), wait_tries=1)`,**非 MuMu 句柄树会抛异常** → 回落 `None`。
   注释原文:「PC 桌面版窗口不满足句柄树校验,自然回落旧链路」。

而 `PcBackend` 的方法体全是 `NotImplementedError`(`backend.py:39-52`,注释写着
「call-sites keep backend=None under default pc mode」)——**PC 模式下 backend 恒为 None**。

> **你本机属于路径 B**:日志里是「使用PrintWindow模式捕获」,说明 hwnd 没通过 MuMu 句柄树校验、
> `backend=None`。虽然下拉里显示的是「PC桌面版 · 阴阳师-MuMu模拟器专版」,但那只是**客户端名**,
> 走的是窗口截图链路。

### 2.2 路径 B 的内部顺序(`GetDC.capture_window()`)

```
1. 最小化检查(IsIconic)  →  是则弹提示 + 直接 return None   (GetDC.py:256-258)
   ※ 注意:这一步在选模式之前,所以最小化【不会】触发模式回退
2. 用 settings.BACKEND_GET_IMG_MODE 抓屏                        (GetDC.py:262, 280)
3. 判成功:img 不为 None 且 np.mean(img) > 5                     (GetDC.py:281)
4. 失败 → 换另一种模式再抓一次                                  (GetDC.py:287-289)
5. 这回成功 → 【把 capture_window_mode 永久改写成 fallback】     (GetDC.py:293-297)
6. 两种都失败 → 记 “所有捕获方法失败” + 进入 30s 冷却,不再弹窗   (GetDC.py:300-304, 92)
```

PrintWindow 模式内部还有一层回退(`capture_window_printwindow`):

- 先用 `PW_CLIENTONLY`(只渲染客户区,位图按客户区尺寸建);
- `PrintWindow` **返回失败**才回退 `PW_RENDERFULLCONTENT`(`GetDC.py:388-397`);
- 全黑判定 `np.mean(img) < 5` → 判失败、`return None`(`GetDC.py:406-409`)。

> ⚠️ 已知设计缺陷(作者自己在 `GetDC.py:45-52` 写明了):`PW_RENDERFULLCONTENT` 会把标题栏
> 渲染进「客户区尺寸」的位图里,底部 47px 游戏内容被挤掉。所以它只在 `PW_CLIENTONLY`
> **彻底失败**时兜底,**不会**在全黑时使用——错位的图比返回 None 更糟。

### 2.3 坐标系与标题栏偏移(改素材时最容易踩)

- 模板图/区域坐标一律是**客户区逻辑坐标**(`backend.py:9` 注释)。
- 但截图**可能含标题栏、也可能不含**(取决于走的哪个 flag / 哪条回退路径),所以偏移不能写死:

```python
title_bar = 窗口高 - 客户区高                        # recognition_opencv.py:97-105
dy = effective_client_dy(截图高, 客户区高, title_bar)  # GetDC.py:45-57
    # 截图高 >= 客户区高 + title_bar - 2  →  返回 title_bar(截图含标题栏)
    # 否则                                →  返回 max(0, 截图高 - 客户区高)
```

- **1280×720 陷阱**:走路径 A(IPC)时截图是 1280×720,和客户区尺寸不同;而绘卷模块的
  `BASE_W/BASE_H = 1920/1080` 是另一套基准(`huijuanshuafen/base.py:27-28`)。
  换路径/换分辨率时要留意这三套基准:客户区实际尺寸、1280×720、1920×1080。

### 2.4 窗口尺寸

- 窗口检测会把窗口调整到**目标尺寸**,取自设置里的「自定义同步时的窗口大小」
  (`custom_res_width/height`,**默认 1441×812**)。
- **同步流程**读它(`main_window.py:728-740`),**单开窗口检测**也读同一个值
  (`WindowChecker.py:239-240`)—— 两处统一。
- 若目标尺寸被窗口/模拟器拒绝(如 MuMu 锁 16:9),会**吸附到最接近的可达尺寸并写回设置**,
  避免每次检测都在两个尺寸间来回横跳。

> 修复前 `connect_all()` 是**无参硬编码 1404×834**(`WindowChecker.py:142`),所以你在设置里改成
> 别的值,对单开窗口检测毫无影响 —— 这是"改了没反应"的一个真实原因。现已修正。

## 三、为什么"有的截图配置被锁死、改不动"

这是你问的核心。核实下来有 **6 个不同原因**,机制完全不一样:

### ① `capture_window_mode` 会被程序自己改回去(最常见)

`GetDC.py:293-297`:一旦「换另一种模式」成功,程序就把你的设置**永久写回**成那个 fallback:

```python
if settings.BACKEND_GET_IMG_MODE != fallback_mode:
    logger.info(f"切换到{fallback_mode}模式")
    settings.update_settings('capture_window_mode', fallback_mode)
```

**表现**:你把模式改成 PrintWindow → 某一次瞬时失败(窗口刚好被销毁/黑屏)→ 程序翻成 BitBlt
并覆盖文件 → 你觉得"改了被锁死,自己变回去"。

**这不是 bug,是作者的有意设计**(想让程序自己在能用的模式上稳定下来),但它没区分"瞬时失败"
和"这个模式在你的机器上根本不行"。

### ② 设置页下拉框不刷新 → 选同名项不发信号(UI 层"锁死")

`settings_page.py:102-109`:下拉框**只在初始化时**读一次 `capture_window_mode` 来设当前项,
之后再没有刷新逻辑(全文件只有这一处 `setCurrentIndex`)。

于是:程序被 ① 自动改成 BitBlt 并写回文件,而下拉框**显示的还是 PrintWindow**。此时你
再去下拉里选「PrintWindow」——它本来显示的就是 PrintWindow,Qt 的 `currentTextChanged`
**不会触发**,于是不会保存。看起来就是"怎么点都没反应"。

**绕过办法**:先选另一个值,再选回来(制造一次真实变化);或者退出程序直接改文件。

### ③ `settings.json` 运行中手改会被覆盖

见第一节:`update_settings()` 写的是整份内存 dict。**运行中手改的键,会被下一次保存整份冲掉。**

### ④ 这两个键压根没人读(纯摆设)

全量核对了 21 个源文件(`grep` 过 `tools/`、`app/`、`pipeline/`、`emulator/` 全部已取文件):

| 键 | 定义处 | 消费者 |
|---|---|---|
| `screenshot_method`(默认 `nemu_ipc`) | `settings.py:48` | **没有任何代码读取** |
| `control_method`(默认 `window_message`) | `settings.py:49` | **没有任何代码读取** |

它们只在 `settings.py` 里被「定义 + 更新」,没有任何调用点。**改它们不会有任何效果。**
(实际走哪条截图路径由 `hidden_window` + `backend` 决定,见 2.1;方法名不是配置项。)

### ⑤ `custom_res_width/height` —— 现已全流程生效

- **同步流程**:`start_sync()` 读它作为调整目标(`main_window.py:728-740`,每次同步重读配置文件);
- **单开窗口检测**:`connect_all()` 也读同一个值(`WindowChecker.py:239-240`);
- **默认值 1441×812**;目标尺寸被窗口拒绝时会吸附到可达尺寸并写回设置。
- 它**没有被导出**成模块级变量(`settings.py` 里没有 `CUSTOM_RES_*`),所以别的模块引用不到,
  但上面两条读取路径都直接读 `settings_data`,改动即时生效。

→ 修复前 `connect_all()` 是**无参硬编码 1404×834**,所以在设置里改成 1920 对单开检测**毫无影响**;
改成 1404×834 恰好"看起来能用",只是因为那个硬编码值就是 1404×834。**现已修正,两处统一读设置。**

### ⑥ `emulator_type` / `handle_spec` 没有界面,且要重启

- 二者**确实有消费者**(`OnmyojiAuto.py:97,101`、`recognition_opencv.py:54,58`)✓
- 但 `settings_page.py` 里**没有对应控件**(全量 grep 无命中)→ 只能改文件
- 而 `settings.json` 只在启动时读 → **必须重启**
- 它们不在你本机文件里,所以走默认:`emulator_type='pc'`、`handle_spec='auto'`

> **你要的那个"MuMu 完全最小化也能跑"就靠 `emulator_type`**:设成 `"mumu12"` 才会挂上
> IPC backend(`OnmyojiAuto.py:97`)。但注意:设了之后截图会切到 **1280×720 参考系**,
> 和现在的客户区坐标系不是一回事。

### ⑦(架构层)本地 `.py` 改了不生效

`OAT/app`、`OAT/tools`、`OAT/utils`、`OAT/pipeline` 这些模块**编译进了 exe**(Nuitka
`--standalone`),磁盘上的 `.py` 不被导入。所以"改源码修 bug"在本机是无效的,必须重新打包。
详见同目录 `upstream-fix/README-上游修复说明.md`。

## 四、实操:正确的改法

### 想固定抓屏模式

1. **完全退出** OAT;
2. 编辑 `OAT/tools/settings.json` 的 `capture_window_mode`(`"PrintWindow"` 或 `"BitBlt"`);
3. 启动,开挑战,看日志出现哪一行:
   - `使用PrintWindow模式捕获` / `使用BitBlt模式捕获`(`GetDC.py:268`);
4. 如果过一会儿又出现 `切换到XXX模式`(`GetDC.py:295`)——说明**第一次尝试真的失败了**,
   程序已把文件改回去。这时别硬改:**那个模式在你的窗口上确实不稳**,顺着它用另一个即可。

### 排查"抓不到图"

按顺序看日志这 4 行:

| 日志 | 含义 | 对策 |
|---|---|---|
| `窗口处于最小化状态,无法捕获图像`(`GetDC.py:242`) | 最小化了。这条**不会**触发模式回退 | 恢复窗口 |
| `PrintWindow捕获到的图像可能是全黑的`(`GetDC.py:408`) | 该 flag 渲染空白 | 让它回退,或改用 BitBlt |
| `XXX捕获失败,尝试YYY方法`(`GetDC.py:288`) | 主模式失败,正在回退 | 观察是否切成功 |
| `所有捕获方法失败`(`GetDC.py:300`) | 两条路都挂了 | 多为**窗口句柄已失效**(见下) |

**句柄失效的典型特征**:日志里同时出现 `(1400, 'GetClientRect', '无效的窗口句柄。')`
(`GetDC.py:216`)。这时窗口已经没了,重启游戏/模拟器后点一次「刷新窗口」重新取句柄即可。
(`upstream-fix` 里的 `WindowChecker.py` 补丁就是修这个:让失效句柄自动重新解析,而不是每轮抛异常。)

### 想加/改模式

1. 在 `OAT/source/` 下建目录(拼音名),放模板图 + `config.json`;
2. 在 `OAT/source/mode.json` 里登记:单模式写 `"模式名": "目录名"`,有子模式写
   `{"default": "目录名", "子模式A": "目录A"}`;
3. **重启程序**(`mode.json` 启动时读入 `MODE_MAPPING`);
4. 细节见 `OAT/source/自定义配置教程.txt`。

> 你之前遇到的 `不支持的模式: 最新版本活动` 就是因为**先建了目录、忘了登记 mode.json**;
> 该模式(PVE)和 `source/PVE/` 都是你自己加的,上游没有。

## 五、一句话总结

- 截图有**两条路**:窗口截图(PrintWindow/BitBlt,客户区坐标系)和模拟器 IPC(1280×720),
  分岔点是 `hidden_window` + `backend` 是否为 None(`recognition_opencv.py:116-126`)。
- "配置被锁死"的真相有 6 种,最常见的是 **`capture_window_mode` 被程序按一次瞬时失败自动改写**
  (`GetDC.py:293-297`),其次是 **设置页下拉框不刷新导致选同名项不发信号**(`settings_page.py:102-109`)。
- `screenshot_method`、`control_method` 是**纯摆设**,改它们没有任何作用。
- `settings.json` / `mode.json` 都是**启动时读一次**,且 `settings.json` 运行中手改会被整份覆盖
  —— **改这两个文件必须先退出程序**。
